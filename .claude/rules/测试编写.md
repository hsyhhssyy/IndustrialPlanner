## 禁止修改测试

### 定义

以下类型的错误**绝对不允许**直接修改测试代码来"修绿"：

- **测试断言失败（test failed）**：即测试逻辑未通过，期望值与实际值不匹配。
- **运行时异常**：测试执行过程中抛出的未捕获异常。

### 允许直接修复的错误

以下类型属于代码正确性问题，**可以直接修改**，无需询问用户：

- **TypeScript 类型错误（type-check error）**：类型不匹配、缺少导入、接口变更导致的编译错误。
- **Lint 错误**：ESLint 规则违反。

### 测试失败时的处理流程

测试失败可能原因：

1. **测试漂移**：实现变更后测试期望值未同步更新。
2. **回归失败**：实现变更引入了真实 bug。

当测试失败时，必须：

1. **进行初步原因判断**，区分是测试漂移还是回归失败。
2. **通知用户**，告知：
   - 哪些测试未通过
   - 每个测试的测试项目（它验证什么行为）
   - 初步判断的失败原因（漂移 or 回归）
3. **等待用户指令**，不得擅自修改测试断言或测试逻辑。

### 随模块变更同步修改测试（允许）

当用户明确要求修改某个模块的实现时，对应的测试可以同步更新。
此时修改测试的**前提**是：修改原因是"模块接口/行为变更"，而非"测试未通过"。

**执行结束后必须列出**：

- 修改了哪些测试文件
- 每个测试文件的测试项目（它验证什么行为）
- 是因为什么模块的什么变更触发了本次测试修改

## 创建新测试

创建新测试时，请阅读：
.docs/common/测试/测试架构设计通则.md

### 测试文件命名

测试文件放在 `src/tests/` 下对应子目录中，文件名以 `.test.ts` 结尾。

### 运行命令

项目配置了两个 vitest project：

```bash
# 常规测试（默认并行，开发时常用）
npx vitest run --project normal

# 蓝图文件测试（串行，单文件耗时数分钟，仅做大回归时使用）
npx vitest run --project blueprint
```

> **注意**：Simulation 层所有测试都要求"蓝图驱动端到端"（在测试代码中动态构造最小蓝图）。
> 此处的 `blueprint` project **仅指**通过预制蓝图 JSON 文件（位于 `public/blueprints/`）运行的大规模串行回归测试，与动态构造蓝图的普通 simulation 测试是不同的概念。
> 当用户说"蓝图测试"时，指的就是这些蓝图文件测试，不要混淆。

### 分层策略

不同模块的测试策略参见 `测试架构设计通则`：

- **Simulation**：蓝图驱动端到端，禁止 mock Worker/SimulationHost。
- **蓝图文件测试（blueprint project）**：使用预制蓝图 JSON 文件，设备规模大、耗时长（单文件数分钟），串行执行，属大回归测试。未来新增的系统蓝图均在此添加。
- **App / Editor**：Playwright E2E + 双重验证，使用真实浏览器事件。
- **Renderer**：分层处理——纯几何计算去 mock、Sprite 视觉比对、完整场景集成。
- **Shared**：纯逻辑单元测试，不依赖 DOM/Canvas。
