## 请按以下顺序执行：

1. 先读取 `.docs/stages/` 下编号最新的 `stageN` 目录，理解当前阶段的目标、范围、顺序、边界和未完成事项。
2. 先告知我你的理解：当前阶段目标、当前 session 边界、下一步应从哪里开始。
3. 当我随后提出新的需求、调整或 Bug 修复时，优先对齐最新 stage 文档中的实施计划与约束，不要越过当前阶段边界随意扩展范围。
4. 如果我的新要求与当前 stage 文档冲突，先明确指出冲突点，并先同步 stage 文档，再继续实现。
5. 每完成一个明确步骤，都要同步更新最新 stage 目录下的相关文档，至少记录本步完成内容、状态变化、影响范围和下一步衔接点；这里的“明确步骤”应是一次边界清晰、可单独说明目标和状态变化的执行动作。
6. 涉及跨需求或 owner 边界时，文档回写要明确真相层归属，避免把运行态、渲染态或会话态职责写错。
7. 代码改动和文档改动属于同一份交付，不能只改代码不更新文档，也不能只更新文档不落地实现。
8. 每完成一个明确步骤后，在同步完对应文档与代码后，直接执行一次 Git 提交；不要把多个已完成步骤合并成一次提交。即使该步完成后软件暂时不可用、无法编译或存在 bug，也仍应按步提交。
9. 每次提交都必须同时包含该步骤对应的文档改动和代码改动；若当前步骤暂时只有一侧改动，先补齐同一步所需的另一侧交付，再提交。
10. 回复我时，说明本次改动更新了哪些 stage 文档，以及这些更新如何反映当前实现进度。
11. 提交信息应明确对应当前步骤的目标或结果，避免使用无法体现阶段进度的模糊信息。

## 重要说明
1. 如果你发现用户的问题基于错误前提，要说出来。你是协作者，不是执行机器。用户从你的判断中获益，而不只是从你的服从中获益。
2. 当某个需求或 Bug 在单一路径上被提出或暴露时，不要默认将其实现为该路径的专用逻辑或例外修补。先判断这是否意味着共享函数、公共接口或底层抽象需要同步升级；若存在这种可能，应主动指出并优先采用统一演进方案。
3. 当实现方向发生变化时，不要仅追加新改动。应清理与当前方案不一致的前序实现，确保最终代码只保留收敛后的方案。
4. 我接受在开发或重构过程中，软件出现一段时间的不可用、无法编译或存在 bug，只要在开发结束时恢复正常即可。因此你在安排重构或需求开发步骤时，不需要为了保证软件始终可用而采取过于保守的方案，或拆出过多步骤；应优先考虑如何高效地完成开发或重构。
5. 如果你在进行 Bug 修复，请不要在用户描述 bug 后立刻边推测边修复。如果当前证据不足以精确确定问题所在，你应先给用户提供调试步骤，帮助收集更多信息以确认问题，再继续修复；如果该步骤已形成明确的定位动作，也应按同一步要求同步文档、代码并提交。
