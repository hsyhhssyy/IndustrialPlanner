# 版本更新日志写作 Prompt

## 任务说明

你将撰写一份《浏览器里的集成工业》的版本更新日志。用户会提供本次版本需要介绍的**重点功能列表**，你需要基于这些功能完成一篇完整的更新日志。

---

## 功能优先级与结构

1. **重点功能**：用户给出的功能列表即为重点功能，按用户给出的顺序排列——最先提到的最重要。
2. **其他变更**：用户未提及但属于本版本变更的内容，统一放在日志末尾的 `## 其他内容` 章节下，尽量简洁概括，一两句话带过即可，不要展开详述。
3. **去重**：如果某个变更已经作为重点功能在前文详述，`其他内容` 中不再重复。

---

## 语气与风格

- **参考贴吧 / NGA 的社区分享帖语气**，但不要提及任何具体平台名称或平台相关概念（因为日志会同步发布到 B站专栏、贴吧、NGA、森空岛、TapTap 等多个平台）。
- 语气可以轻松、有交流感，但**不要过于口语化**，整体保持正式但不死板。
- **严禁**出现以下内容：
  - 卖惨、自曝缺陷、自我贬低
  - 与软件功能无关的个人情绪表达
  - 对游戏官方（鹰角）的抱怨或负面评价
  - "我还没玩到这里所以图不好看"之类暴露作者个人状态的表述
- 可以适当使用玩家社区常用的表达方式（如"小伙伴们""各位玩家"等称呼），但不宜过度。

---

## 配图规则

日志中可以配图，方式有两种：

### 方式一：Playwright 自动截图

如果你认为某个功能可以通过 Playwright 截图来展示，启动 Playwright 截图。截图要求：

- **聚焦功能**：截图应聚焦在需要介绍的功能上，而不是整个页面。
- **保留环境**：不能只截功能本身，需要保留一部分周围 UI 环境，让读者知道这是在哪里。
- **配说明文本**：每一幅截图下方必须配一行说明文字，格式为：
  ```
  ![图片描述](./img/xxx.png)
  > 图：说明该截图展示了什么场景下的什么功能。
  ```

### 方式二：占位图

如果你觉得某个功能比较复杂、拿不准什么图能表达清楚，但又确实需要配图，可以插入占位文字：

```
[一张XXXXXX的图片]
```

描述清楚你希望这张图片传达什么内容，后续会由人工配图。

## 技术规范

以下规则继承自项目的 changelog 写作规范，必须遵守：

### 物品/设备名称

日志中涉及任何物品、设备、配方名称时，**必须**到 `src/shared/i18n/zh-cn/registry.ts` 中查询官方中文名称，严禁自行翻译或编造。

### Bug 修复描述

`fix:` 类条目应描述用户看到的错误现象，而非技术根因。例如：
- ✅ `修复反应池无法选择输出端口物品的问题`
- ❌ `修复反应池端口过滤条件不符的问题`

### 条目格式

- 每条以 `- ` 开头。
- 简短描述改动内容，不写技术实现细节。
- `dev:` 类内部改动（构建、配置、CI 等）不出现在 changelog 中。

最终输出为一份完整的 Markdown 更新日志文件，保存到 `public/changelog/` 目录下，并更新 `public/changelog/index.json`。
