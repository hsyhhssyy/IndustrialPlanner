# EDA 算法优化循环

## 调用语义

- `/eda-algorithm-optimization` 之后的全部文本自动作为第三节“背景、问题、事实与目标”；不要在技能正文里预置具体任务，也不要要求用户再套模板。
- 输入为空，或缺少可验收目标（目标物品/指标、约束、验收口径）时，停止并要求补充；不要自行假设目标。
- 算法实现文件（`src/blueprint-planner/` 与 `src/blueprint-planner-worker.ts`）存在未提交改动时，按第四节执行硬性阻断：提示用户先提交，提交后再继续。
- 调用本技能即构成第三节所述执行授权，不是“只分析”请求。除明确阻塞外持续执行，不等待逐轮确认。
- 开始前用一句话复述目标、验收口径和授权边界；首轮诊断后汇报基准与实验方向，然后继续执行。

## 一、授权范围

1. 授权创建专用分支和 worktree，并读取、编辑你自己新建的 worktree。本段同时作为根规范第 8 条所要求的再次读取授权；不要访问其他既有 worktree 或其他分支的文件。
2. 授权必要的分支创建、`git worktree add`、算法修改、编译，以及将专用构建发送到远程 Windows 运行。
3. 不授权 Git 提交、推送、发布或修改正式部署。
4. 先检查当前工作区和 Git 状态，避免覆盖其他任务的未提交改动。不要擅自将这些改动混入实验构建。算法实现文件存在未提交改动时，停止并提示用户先提交；不要自行执行 Git 提交。
5. 这是持续优化任务，不要只给方案或只运行一次实验就结束。遇到无法独立解决的阻塞时，保存检查点、清理资源，并明确说明阻塞。

## 二、实验要求

1. 扩大初始面积是你应该最后选择的方案，只有实在没有其他方向时才可以选择。
2. 每次修改后除了测试你修改的物品，还应该随意选择一个过往已通过物品进行复测，确保算法本身没有劣化。
3. 开始后请先给出你核验到的基准、首次诊断结论及第一轮实验方向，然后持续执行。每轮用证据说明保留或否定该改动；达到目标后交付可审查的代码改动、实验对照和剩余风险。
4. 每轮改动后如果修复未达标，不能直接在该轮改动的基础上继续修改，而是需要分析本轮的改动是否有价值吸收，如果没有吸收价值，则应直接丢弃，重新从代码基线开始修改。如果吸收，则吸收进该临时分支并成为新的代码基线。

## 三、背景、问题、事实与目标

**本节内容 = 用户在斜杠命令后输入的文本**。若运行环境提供 `$ARGUMENTS` 占位符，则本节直接取该变量；否则取命令后的原始文本。

示例：`/eda-algorithm-optimization 把赤铜耐压罐 30/min 的首解压到 20M 内，面积不超过 320，保持现有产率与验收口径`

执行时以该文本为唯一任务来源：

- 提取并记录：背景、问题、已知事实、目标、硬约束、验收标准、禁止项。
- 文本中的明确要求优先于本技能的一般建议；但不得越过第一节授权范围，也不得突破第六节资源与安全边界。
- 用户未指定的实验参数（种子、并发、预算、复测用例）由执行者按现有设施默认值确定，并在首轮汇报中列明。
- 不得把主工作区未提交改动默认视为任务背景；它们只作为工作区状态记录。

## 四、启动与基线核验

1. 阅读项目根目录的 `AGENTS.md`、`.docs/common/项目模块隔离开原则发规范.md`（涉及新增函数、类型、模块或跨模块引用时必读），以及与目标相关的 EDA 文档和现有测试入口。
2. **算法范围洁净检查（硬性阻断）**：创建 worktree 前执行：

   ```bash
   git status --short -- src/blueprint-planner src/blueprint-planner-worker.ts
   ```

   这里只检查 EDA 算法实现和算法 Worker 入口，不检查全项目，也不默认阻断 `src/registry`、`src/simulation`、`src/shared` 等非算法目录。若首轮诊断确认本轮还会修改其他算法实现路径，把这些路径追加到本次检查命令；不要扩大到全项目。

   上述算法路径存在已暂存、未暂存或未跟踪改动时，立即停止，列出文件并提示用户先提交，提交后再继续。不得自行执行 Git 提交，也不得用主工作区未提交改动替代 HEAD 基线。
3. 用户完成提交后，重新执行 `git status` 与 `git rev-parse --short HEAD`，确认检查范围已干净，并把新 HEAD 记录为实验基线。
4. 只读检查工作区与 Git 状态：`git status --short --branch`、`git rev-parse --short HEAD`、`git worktree list`、`git log -1 --oneline`。记录其他未提交改动，但不混入实验构建。
5. 创建专用 worktree 与分支，路径必须唯一，不覆盖已有目录：

   ```bash
   git worktree add /home/coder/IndustrialPlanner-Worktrees/eda-optimize-<yyyyMMdd-HHmm> \
     -b eda/optimize-<yyyyMMdd-HHmm>
   ```

6. 记录基线身份：分支、commit、目标算法版本（当前为 `src/blueprint-planner/search-policy.ts` 中的 `PLANNER_ALGORITHM_VERSION`）、目标物品与产率、种子、初始面积、计算预算、并发、GPU 开关、验收引擎。
7. 在 `.temp/eda/optimize/<run-id>/baseline/` 保存基线源码快照（至少包含本轮可能改动的算法目录）。丢弃轮次时用文件快照恢复，不使用 `git reset`、`git restore`、`git checkout`、`git clean` 或 `git apply`。
8. 在任何算法改动前完成一次基线实测，确认现有入口、构建、远程部署和结果回收可用；同时记录一个过往已通过物品的结果作为回归基线。
9. 首次汇报必须包含：核验到的基准、首次诊断结论、第一轮实验方向、工作区未提交改动对基线的影响。汇报后继续执行，不等待确认。

## 五、实验循环

每轮严格按顺序完成，不允许跳步：

1. **定位瓶颈**：用代码路径、失败分布、性能计数或历史结果指出具体瓶颈，不靠猜测。
2. **提出单一可证伪假设**：说明改动预期改善哪个指标、为什么、如何判定有效。
3. **修改算法**：只改与该假设相关的代码；保持模块隔离和现有契约，不做补丁式绕行。
4. **编译**：至少执行 `npm run build`（含 TypeScript 检查）；失败则修复后重跑，不进入实测。
5. **部署到远程 Windows**：只部署本轮专用构建，使用独立端口、浏览器 profile 和隧道，不触碰正式部署或他人服务。
6. **实测**：先跑目标物品，再跑随机抽取的过往通过物品；两组都使用正式 Host 验收，不用阶段最佳、未验产候选或自造指标替代。
7. **分析结果**：对照基线，区分真实改善、噪声、环境故障和回归劣化。
8. **吸收或丢弃**：按下方规则处理，不得在未判定的失败改动上继续叠加。
9. **记录**：按第八节模板落盘证据，然后进入下一轮。

### 吸收与丢弃

- **本轮未达标时，禁止直接在本轮改动上继续修改。**
- **有吸收价值**：说明具体保留哪一部分、依据是什么；保留改动在 worktree 工作区，并更新基线快照，使其成为新的代码基线。不执行 Git 提交，最终交付为可审查的未提交 diff。
- **无吸收价值**：把本轮 diff、结果和失败证据归档到 `.temp/eda/optimize/<run-id>/discarded/R<N>/`，再按基线快照恢复源码，从干净基线重新开始。
- **回归劣化**：目标指标改善但随机回归物品失败或明显劣化时，本轮不得吸收，除非用户明确接受该代价并记录原因。
- 吸收只接受完整、可解释、可复现的改动，不接受“先留着以后再修”的半成品。

### 扩大面积是最后手段

- 默认禁止通过扩大初始面积、放宽最终验收面积、降低产率、改变仿真口径或更换验收引擎来“达标”。
- 只有证明其他方向均无效，并保留对照证据后，才可把面积调整作为单独一轮最后手段；该轮必须明确标注，不得与其他改动混合。

### 随机回归复测

- 每轮从未参与本轮改动的已通过物品中随机抽取至少一个；记录抽取方式或随机种子，保证可审计。
- 不得每轮固定挑同一个“最稳”用例；若历史不可用，从 `src/shared/eda-regression/cases.json` 的固定用例中随机抽取。
- 回归结果与目标结果分开记录；回归用于证明算法没有劣化，不能替代目标验收。

## 六、实测通道与资源边界

- **复用现有设施，不新建平行部署通道。** 优先使用仓库已有的远程 Windows 执行器与 EDA 入口；使用前阅读对应技能或脚本的说明，并遵守其串行、锁和清理规则。
- 固定 EDA 用例入口：`npm run test:eda -- --list` 查看用例，`npm run test:eda -- --case <id>` 执行；需要有界面浏览器，禁止无头模式。
- 任意物品或正式 Host 验收：可复用 `.agents/skills/eda-all-items-audit` 的 Windows 执行设施，按其 `prepare --items` / `run` 流程执行。该设施会把轮次写入正式全物品历史；若本轮只是算法实验而非正式审计，先向用户说明副作用并取得同意，或改用不写正式历史的固定用例通道。
- 远程 Windows 访问本轮构建时，使用专用非 5173 端口与 SSH 反向转发/隧道；端口冲突时改用其他空闲端口并记录。
- 上述通道都无法表达目标时，停止并报告所需的最小扩展；不得静默自建第三套部署器。
- 每轮实测至少保存：源码改动指纹、完整输入、原始结果、首解/次解次数、面积、验收报告、耗时、硬件与并发、随机回归结果。
- 浏览器、Playwright 会话、隧道、专用开发服务器和临时脚本必须在 `finally` 中清理；失败、超时、中断也要清理，并核对进程与端口无残留。
- 测试中间产物只放 `.temp/`；一次性脚本放 `.temp/.trash/` 并在结束后清理。不得污染工作区或占用 5173。

## 七、停止条件与交付

达到以下任一条件时停止循环并交付：

1. 用户目标已达成，且随机回归通过。
2. 取得证据证明方向需要调整：连续多轮同一失败模式且没有新的可检验假设，或现有设施无法表达目标，或目标本身被证明不可达/代价不可接受。
3. 用户明确要求停止。
4. 遇到无法独立解决的阻塞：保存检查点、清理资源、说明阻塞原因和需要用户决策的最小问题。

交付必须包含：

- 可审查的代码改动：文件列表、核心 diff 摘要、未提交状态声明。
- 实验对照：基线 vs 最终结果，以及每轮保留/丢弃记录。
- 剩余风险：未覆盖边界、回归缺口、性能或维护代价、回退方式。
- 复现方式：分支/worktree、构建命令、实测入口、输入与证据目录。

**不执行 Git 提交、推送、发布或正式部署变更。**

## 八、每轮记录模板

```md
### R<N> <一句话假设>
- 瓶颈证据：
- 改动文件：
- 编译结果：
- 目标实测：物品 / 种子 / 预算 / 首解 / 次解 / 面积 / 验收 / 耗时
- 随机回归：物品 / 结果 / 是否劣化
- 结论：保留 / 丢弃
- 新基线：说明吸收内容或恢复到的基线快照
- 证据目录：.temp/eda/optimize/<run-id>/R<N>/
```

## 九、禁止事项

- 只给方案、只跑一次实验或遇到首个失败就结束。
- 在未达标且未判定的改动上继续叠加修改。
- 把扩大面积、降低产率或放宽验收作为首选。
- 在算法实现文件有未提交改动时直接开始实验，或自行执行 Git 提交。
- 混入主工作区未提交改动，或读取其他 worktree / 其他分支的文件。
- 用阶段最佳、未验产候选或自造统计替代正式验收结果。
- 占用 5173、污染项目文件、跳过资源清理。
- 执行 Git 提交、推送、发布或修改正式部署。
- 隐藏失败、把未完成包装成完成，或把环境故障写成算法结论。
