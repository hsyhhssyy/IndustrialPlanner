# 测试处理规则

## 禁止修改测试来修绿

以下错误不得直接通过修改测试代码处理：

- 测试断言失败：期望值与实际值不匹配。
- 运行时异常：测试执行过程中抛出未捕获异常。

以下错误属于代码正确性问题，可以直接修复，无需询问用户：

- TypeScript 类型错误，例如类型不匹配、缺少导入、接口变更导致的编译错误。
- ESLint 错误。

## 测试失败处理流程

测试失败可能是测试漂移，也可能是实现回归。必须：

1. 初步判断属于测试漂移还是回归失败。
2. 通知用户哪些测试未通过、各测试验证什么行为，以及初步失败原因。
3. 等待用户指令，不得擅自修改测试断言或测试逻辑。

## 随模块变更同步修改测试

用户明确要求修改模块实现时，可以同步更新对应测试，前提是测试修改源于模块接口或行为的明确变化，而不是为了让失败结果转绿。

完成后必须列出：

- 修改的测试文件。
- 每个测试文件验证的行为。
- 触发测试修改的模块变化。

## 创建新测试

新测试必须遵循 `.docs/common/测试/测试架构设计通则.md`。测试文件放在 `src/tests/` 对应子目录，文件名以 `.test.ts` 结尾。

## 单项测试命令

常规测试：

```bash
npx vitest run --project normal
```

预制蓝图 JSON 大规模串行回归测试：

```bash
npx vitest run --project blueprint
```

Simulation 层测试使用在测试代码中动态构造的最小蓝图，属于蓝图驱动端到端测试，但不等于 `blueprint` project。`blueprint` project 专指使用 `public/blueprints/` 中预制蓝图 JSON 的大规模串行回归测试。用户说“蓝图测试”时，指后者。

## 分层策略

- Simulation：蓝图驱动端到端，禁止 mock Worker 或 SimulationHost。
- Blueprint project：使用预制蓝图 JSON，设备规模大、耗时长、串行执行；新增系统蓝图在此添加。
- App / Editor：Playwright E2E + 双重验证，使用真实浏览器事件。
- Renderer：纯几何计算去 mock、Sprite 视觉比对、完整场景集成。
- Shared：纯逻辑单元测试，不依赖 DOM 或 Canvas。
