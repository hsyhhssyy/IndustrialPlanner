# 提交执行规范

## 终端环境与认证前置条件

1. 在 Codex / VS Code 环境中，Git 凭据可能由当前项目的活动集成终端通过 `GIT_ASKPASS` 和 `VSCODE_GIT_*` 注入；普通执行 shell、登录 shell 或交互 shell 均不等同于该终端环境。
2. 执行远端认证预检和 `./commit-all.sh` 时，必须继承当前项目活动集成终端的完整环境。定位终端时以工作目录为当前仓库且环境包含 Git AskPass 注入变量为依据，不得硬编码进程 ID。
3. 不得打印、记录或写入终端环境变量值，也不得把凭据拼入命令行、提交信息或临时文件。
4. `gh auth status` 不能证明 Git 推送是否可用；VS Code Git AskPass 可在 GitHub CLI 未登录时正常工作。认证结果必须以 Git 命令为准。
5. 运行提交脚本前，递归识别脚本会处理的根仓库、已初始化 submodule 和独立 `.temp` 仓库。对其中配置了 upstream 的仓库，使用同一终端环境执行 `git -C <仓库路径> push --dry-run`。
6. 根仓库和任一 submodule 的 dry-run 必须成功；认证、连接、权限、non-fast-forward 或其他任意失败都必须在提交前停止，不得对这些仓库执行 pull、merge 或 rebase。
7. `.temp` 是唯一允许合并的仓库。它的 dry-run 成功，或仅因远端领先导致 non-fast-forward / fetch-first 拒绝时，均可进入提交阶段；认证、连接、权限等其他失败仍必须停止。
8. `.temp` 的拉取与合并只能由 `commit-all.sh` 内置流程执行，不得由 Agent 手工执行。不得把该例外扩展到根仓库或任何 submodule。
9. 找不到符合条件的活动终端，或出现上述不可接受的预检失败时，必须在任何提交发生前停止并报告；不得修改 remote、绕过项目脚本或改用直接提交。

## 执行步骤

1. 运行 `git status` 和 `git diff --stat`，确认当前改动范围。
2. 按“终端环境与认证前置条件”完成全部远端预检。
3. 根据全部改动生成一条简洁的中文提交信息，建议不超过 72 字符，格式为 `类型: 简要描述`。
4. 使用与认证预检相同的终端环境，只运行以下项目脚本提交：

```bash
./commit-all.sh <提交信息>
```

禁止直接执行 `git commit`，也禁止任何绕过项目脚本的提交方式。

5. 脚本结束后，分别检查根仓库、全部 submodule 和 `.temp` 的 `git status --short --branch`，确认工作区干净且当前分支不领先 upstream；记录各仓库最终提交哈希。

## 失败恢复

1. 若已通过预检但脚本仍在某个仓库提交或推送后失败，立即检查根仓库、全部 submodule 和 `.temp` 的状态，明确哪些仓库已提交、已推送或仍有改动。
2. 修复终端环境或远端认证后，只能使用相同提交信息重新运行 `./commit-all.sh`。脚本会跳过无改动仓库并继续未完成部分；不得直接补做 `git commit`。
3. 连续两次使用正确终端环境仍失败时停止，保留现场并向用户报告，不得继续尝试修改 remote、手工合并或绕过脚本。仅 `.temp` 可由 `commit-all.sh` 内置流程自动合并；根仓库和任何 submodule 均不允许自动合并。

## 提交信息规范

### 类型前缀

- `feat:`：新功能。
- `fix:`：修复已有 bug。
- `dev:`：不涉及软件外显功能的内部改动，包括 GitHub Workflow、AI 提示词、项目目录管理、构建脚本、开发工具配置等。修改 changelog 本身也属于 `dev:`，不得在 changelog 中生成“更新 changelog”一类自指条目。

### 正式名称

提交信息或改动日志涉及物品、设备、配方等概念时，必须先在 `src/shared/i18n/zh-cn/registry.ts` 中查询正式中文名称，禁止自行翻译或使用自行理解的名称。

### Bug 描述

`fix:` 应描述用户看到的终端表现，不描述内部根因。

- 正确：`fix: 修复反应池无法选择输出端口物品的问题`
- 错误：`fix: 修复反应池端口过滤条件不符的问题`

### 多项改动

一次提交包含多个独立改动时，提交信息或改动日志必须覆盖全部改动，不得只保留主要条目。
