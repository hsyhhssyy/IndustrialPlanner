## 提交方式强度条款

**禁止直接执行 commit**（`git commit` 及任何绕过脚本的提交方式），只允许运行 `./commit-all.sh <提交信息>` 完成提交。

请使用提交脚本提交代码，提交信息请你自己根据改动总结。

步骤：
1. 先运行 `git status` 和 `git diff --stat` 了解当前改动范围。
2. 根据改动内容，用中文总结一条简洁的提交信息（建议不超过 72 字符，格式如：`类型: 简要描述`）。
3. 运行 `./commit-all.sh <提交信息>` 完成提交。

## 提交信息规范

### 类型前缀
- `feat:` — 新功能
- `fix:` — 修复已有 bug
- `dev:` — 不涉及软件外显功能的内部改动。包括：GitHub Workflow、AI 提示词、项目目录管理、构建脚本、开发工具配置等。**特别注意**：修改 changelog 本身也属于 `dev:`，不应在 changelog 中出现「更新 changelog」这样的自指条目。

### 涉及物品/设备时必须使用 i18n 正式名称
提交信息或改动日志中涉及物品、设备、配方等概念时，必须到 `src/shared/i18n/zh-cn/registry.ts` 中查询其真正的中文名称，严禁使用自行理解或翻译的名称。

### 修复 bug 时描述终端表现，而非根因
`fix:` 的提交信息应直接描述 bug 的终端表现——即用户看到的错误现象，而非内部根因。例如：
- ✅ `fix: 修复反应池无法选择输出端口物品的问题`
- ❌ `fix: 修复反应池端口过滤条件不符的问题`

### 多条改动必须全部列出
如果一次提交包含多个独立改动，提交信息或改动日志中应逐一列出所有改动，不可只选取主要条目省略其余。
