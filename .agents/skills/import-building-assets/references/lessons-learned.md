# 导入错题本

面向按 checklist 执行的 AI。按症状只读对应条目；允许核对字段、比较结果和选择已有命令，需要修改算法、Shader、Registry 或测试夹具时交回维护任务。所有命令在项目根目录执行，路径占位符替换为本批实际路径。

各案例记录 2026-09-14 实跑事实；历史版本和数量只用于解释根因，不是以后导入的固定值或通过证明。核心识别规则以本文件、当前有效实现和正式测试为准；一次性 `.temp` 产物不作为长期证据。

## 图集斜纹

**现象**：预烘焙端口 ON/OFF 图案变成斜线；源图正常，发布图集的宽高及 frame rect 仍能通过结构验收。

**已验证根因**：当时 Sharp 0.34.5 的同一流水线实际先缩放、后补边。旧实现得到 84×37 的 RGBA，却按声明的 83×37 行宽复制，造成逐行偏移。该数字来自 165×74 原帧的半尺寸实例，不能推广为固定裁切值。

**识别方法**：查看 `src/scripts/building-asset-image.mjs` 的有效 `resizeAssetRgba`：应先物化透明补边，再独立缩放，并核对返回的真实宽高、通道与字节数。`validateWebsiteBatch` 只验整页尺寸、引用等，无法单独证明内部像素正确。独立回归位于 `src/tests/scripts/building-assets-site.test.ts` 的颜色补边用例，以及 `src/tests/renderer/building-height-effects.test.ts` 的逐帧发布用例。

处理 checklist：

- [ ] 记录出错资源 ID、发布比例、页文件、frame rect、原件路径及哈希；确认展示的确为本批产物。
- [ ] 按主流程运行本批 `validate`，将结果记为“结构校验”；失败则停止应用。通过后仍保留像素异常为未解决。
- [ ] 核对本次独立像素检查是否真的读取本批目录和全部目标比例；读取正式 `public` 的回归结果不能替暂存批次背书。
- [ ] 当前修复已在共享函数中。若有效实现仍为旧逻辑，或新产物仍错位，停止相关发布并报告维护问题；不加旋转、UV 偏移、人工裁切等局部修补，不照抄历史重发脚本。
- [ ] 维护完成后从已验证原件重新生成，独立期望按行构造补边输入，不复用生产缩放函数或同一错误链；按既定检查范围运行回归与浏览器验证。

**通过标准**：本批逐帧颜色和透明度正确，帧序、时长、pivot 保持协议；真实浏览器载入本批纹理且各规定朝向无斜纹。2026-09-14 的 14 组 / 1,399 帧通过是历史证据，不代替新批验收。

长期证据位于当前共享缩放实现、上述两组正式回归测试及 `.docs/stages/stage2/bugs.md`。尚缺接受暂存目录和全部比例的独立像素 CLI，见 [就绪检查](project-import.md#已知能力缺口)。

## GPU 索引未更新

**现象**：精确模式下真实占用和 CPU 索引已变化，画面仍绘制旧位置的流体。

**已验证根因**：本轮 Pixi 实现中，`setDataWithSize` 的 size 会再乘元素字节数；传入 `byteLength` 导致 GPU 更新越界并残留旧数据。当前 `src/renderer/scene/logistics-baked-flow.ts` 已使用 `indexBuffer.data = indices`。归档的旧调用不能当作现行方案。

**识别方法**：核对浏览器实际资源、JavaScript/WebGL 错误、真实占用、CPU 索引与 GPU 回读四类证据。仅 CPU 数组正确不足以排除上传问题。

处理 checklist：

- [ ] 从既有浏览器验证报告确认测试运行了真实 Renderer，且存在精确模式空洞场景与 GPU 索引回读。
- [ ] 对比 GPU 索引与该帧真实占用；缺回读能力时标为未验证，不在导入中编写 GPU 调试工具。
- [ ] GPU 值不一致或上传报错时，停止视觉验收并报告 Renderer 维护问题；重新下载美术文件不能作为本问题的已验证处理。
- [ ] 若值一致但画面异常，记录资源哈希与截图，按新问题交回定位，不直接归因于本条。

**通过标准**：GPU 索引与真实有液位置对应，精确模式空洞不绘制主体，已有流体内部仍播放；切换设备动画开关不停止物流动画。

当前有效实现位于 `src/renderer/scene/logistics-baked-flow.ts`。2026-09-14 的浏览器回读只说明当时完成过验证，不能视为当前已有可重复的正式验证命令。

## 浏览器场景与端口数量

**现象**：预期 2 ON / 2 OFF，实际出现 3 个连接端口；或固定等待若干秒后，退场仍未完成。

**已验证根因**：本轮临时夹具按每个 `portGroup` 接一根管道，设备有两个输出组，因此多连接一组。另一处固定墙钟等待未考虑仿真快照和渲染帧推进，不能证明已排空。这些是验证场景问题，不能据此修改产品端口或动画规则。

**识别方法**：查看场景记录的 Registry ID、输入/输出方向、实际连接清单、初始槽位及等待谓词。ON/OFF 数量须由场景真实连接推导，不能默认“一组就是一个方向”。

处理 checklist：

- [ ] 在启动浏览器前确认已有可运行场景入口，列出预期连接与断开端口、朝向、操作及结果；只有历史文本归档时按能力缺口报告。
- [ ] 固定场景必须按 Registry 的方向选择目标组并验证数量，不遍历所有组盲目接管。数量不符则记为“场景建立失败”，保留首轮失败，停止此场景验收；不改预期数量迁就错误夹具。
- [ ] 动画完成采用有超时上限的实际状态等待；没有匹配的已验证状态入口则交维护者补齐，不增加固定 sleep 直到偶然通过。
- [ ] 按项目三个 Screen Profile 串行执行，核对实际 viewport、DPR 和触控读数；截图前确认请求的纹理哈希属于本批。
- [ ] 每档成功、失败或中断后，都关闭本档创建的页面、上下文、浏览器、录制与专用服务，并确认进程和端口已释放，再开始下一档。只清理归属明确的资源，使用 5173 以外的端口。

**通过标准**：场景建立符合原定连接和初始状态；有界状态等待成功；三档截图及结构化结果齐全，无相关页面或渲染错误，每档清理已确认。运行时行为按 [物流交付](project-import.md#物流交付)验收，不在此复制另一套状态机规则。

这些历史失败用于固化场景选择与状态等待规则；后续验证以当前场景、结构化结果和项目规定的浏览器产物为证据。

## 原件留存与配色状态

**现象**：`resources` 中已有完整新配色，`public` 及实际显示仍使用旧数据。

**原因与任务边界**：用户明确要求暂不改代码、仅留存配色表。本轮原件收据为 `sourceOnly=true / published=false`，没有更新运行时资源。因此“原件已保存”与“画面已更新”是两个独立状态；不能因画面未变化而补做未经请求的发布。

**识别方法**：读取该批 `_import/source-receipt.json`，核对 `scope / sourceOnly / published`；再分别查看独立配色表、`src/registry/item-definition.ts` 的 `fluidColors` 和 [代码接入状态](project-import.md#配色来源与接入状态)。baked manifest 不再承载按物品配色，不能用它判断 Registry 是否更新。缺少留存专用字段的普通导入收据需查对应发布和应用记录，不能默认未发布。

处理 checklist：

- [ ] 根据用户本次措辞确定仅留存或正式发布，已有明确范围不重复请示。
- [ ] 仅留存任务核对入口：截至本次维护，正式 CLI 未支持该模式。阶段 1 报告缺口，列出 [配色表协议](site-source.md#流体配色表)作为维护验收要求，不改用 `--logistics-only`，不编造 `source-only` 参数。
- [ ] 检查已有留存结果时，对照收据校验原件和索引，记录真实 ID、相态与字段覆盖；未来新增或缺失项按主流程处理，不要求永远为 20 项。
- [ ] 不编辑原件的颜色值，不用颜色 tag 补齐美术数据，不给气体伪造额外来源层。
- [ ] 报告原件留存、Registry 配色应用和运行时素材发布三个状态；正式物流导入必须由 `publish-logistics / validate / apply` 同批闭环。

**通过标准**：留存范围内的原始字节、完整性链、字段覆盖及收据一致，未扩大到 `public` 或代码改造；若任务要求发布，则还须满足正式两层导入和运行时验收标准。

长期来源证据为 `resources/building-assets-site/v1.5-20260914-122929-cst/_import/source-receipt.json`。本轮原件留存使用临时编排，不应标为正式 CLI 已就绪。

## 多个来源批次

**现象**：仅物流更新后，部分高度测试在旧全局来源目录下报缺文件，新物流原件实际保存在新批次。

**已验证根因**：共享高度 manifest 合并了新物流与旧建筑数据；旧测试假定所有项目都来自 `resources/building-top-view-v15.json` 的单一来源。`retained=true` 的未选文件本来就应保持旧字节和旧来源。

**识别方法**：核对报错的完整路径、当前共享高度 manifest、本批 `source-receipt.json` 与 `_import/publish-receipt.json`；区分本批新产物和 retained 项。仅物流模式不会改写全局建筑映射。

处理 checklist：

- [ ] 先查报错路径是否存在于本批根/分级索引及收据，再核对相应原件的本地路径与哈希。
- [ ] 对新产物按本批来源验证；对 retained 项核对原字节摘要及原来源。不得因为目录中有多个 release 就判定混用发布。
- [ ] 本批原件实际缺失或哈希错误时按下载/完整性失败处理，禁止应用。
- [ ] 原件完整而测试固定读旧目录时，记录具体测试与错误路径，报告来源解析维护问题；不复制原件到错误位置，不改写旧收据或全局映射来迎合测试。

**通过标准**：每项来源可追溯，新产物与本批固定索引一致，retained 字节不变；来源读取测试仍失败时检查状态继续为失败，不能以本条解释替代测试通过。

长期验证入口为 `src/tests/renderer/building-height-effects.test.ts`；后续批次必须以当前来源收据和实际测试结果判断。

## 检查失败与基线

**现象**：专项功能验收通过，基础检查中的 normal 仍以非零状态退出。

**已核实规则**：总数相等本身不证明失败集合相同，也不证明全部检查通过；必须比较可比检查范围内的完整失败身份。

**识别方法**：使用实际检查产物，对照本次已记录且检查范围可比的基线。失败身份至少包含测试文件、suite 和完整用例名；错误签名变化或执行环境、检查范围不一致时另行报告，不能只比较数字。

处理 checklist：

- [ ] 按 `simple-check` 或用户指定技能运行检查，不绕过技能直接执行 `npm run test` 或 `tsc -b`。
- [ ] 保存每项退出状态、结果统计、失败明细和日志路径；缺可比基线时写“无法判断是否新增”，不使用错题本中的 28 项作为白名单。
- [ ] 比较失败集合，分别列出新增、仍失败、已消失的项；同名错误发生变化时也列为待定位。当前无统一比较 CLI，不虚构已生成的对账报告。
- [ ] 新增失败或无法归因的变化交回维护任务；旧失败仍如实保留，不改断言、补 mock 或改业务代码消除红灯。
- [ ] 应用已完成但存在失败时使用“已应用但检查未通过”；必需检查或视觉验收未运行时另注明“验证未完成”。记录当前 Git diff，不因测试失败擅自执行 Git 回退。

**通过标准**：各项状态和差异有对应日志支撑；只有本次要求的检查与验收实际通过，才报告“导入完成”。用户认可功能效果与自动化检查结果分别记录。

历史基线不自动适用于下次任务；长期结论只保留比较规则，实际基线来自本次检查产物。

## 批次重试与清理

批次目录只存在于 `.temp/.trash/building-assets-import-<唯一批次>/`，用于本轮下载、派生、验收和应用，不承担版本历史或长期回退职责。成功导入的历史回退统一依靠 Git；任何 Git 文件变更仍须遵循项目授权规则。

| 当前状态 | 执行动作 | 停止条件或完成证据 |
| --- | --- | --- |
| 下载、完整性或发布失败，尚未执行 `apply` | 记录错误后删除本批临时目录；问题解决后建立新批次并重新固定网站发布 | 不复用校验失败的原件、索引或应用清单 |
| `Destination changed after validation` | 停止应用，报告变化的目标路径并保留现有编辑 | 不反复 `validate` 以接受未知编辑后强行覆盖 |
| `apply` 失败或中断 | 停止全部写入，核对正式目录和当前 Git diff，报告残留状态；本批不得再次应用 | 需要回退时等待用户明确授权 Git 操作，不调用历史本地恢复入口 |
| `apply` 成功 | 完成正式文件摘要核对、检查和报告 | 应用清单与正式文件一致；本批不得再次应用 |

清理 checklist：

- [ ] 记录正式文件是否写入、应用与验证结果、仍未完成的项以及当前 Git diff。
- [ ] 需要长期保留的来源信息已经写入 `resources/<来源批次>/_import/`；实现原因、测试契约和已确认缺口已经进入正式代码、测试或项目文档。
- [ ] 关闭本轮浏览器、开发服务器和辅助进程，并确认端口与进程无残留。
- [ ] 工作区状态已核对后删除整个本轮 `.temp/.trash` 批次目录和一次性脚本；不复制到 `.temp/building-assets-import/` 或其他长期临时归档。

**通过标准**：正式目录状态和 Git diff 可解释，临时批次已清理，长期证据位于受版本控制的来源收据、代码、测试或文档中。
