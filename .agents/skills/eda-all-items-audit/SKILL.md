# 全物品蓝图规划 Windows 专项

在 `/home/coder/IndustrialPlanner` 当前工作区运行。入口为：

```bash
node .agents/skills/eda-all-items-audit/scripts/run.mjs help
```

用户仅要求撰写或维护技能时，不启动 `run`。用户明确要求执行全物品测试后，完成准备并自主执行，无需逐项再次确认。测试不自动修改算法、换种子、放宽面积或降低产率，也不提交代码或发布构建。

## 执行

1. 先阅读当前 `AGENTS.md`。执行 `doctor` 核验 SSH、Node、Edge、pywin32、浏览器进程及 4178 端口；远端已有其他 Playwright 任务时等待其结束和清理。Windows 登录桌面、GPU 和工具版本以实际状态为准，旧记录不是当前事实。
2. 首次执行或固定工具需要更新时执行 `setup`。它将本技能 Windows 执行器和本机已安装的 Playwright CLI 同步到 `D:/Endfield-Record/tools/eda-all-items/`，不启动浏览器。每次 `run` 也会检查和同步。连接与目录配置集中在 `policy.json`，不包含凭据。
3. 新的一轮执行 `prepare`，省略面积参数时使用当前 Host 默认公式：

   ```bash
   node .agents/skills/eda-all-items-audit/scripts/run.mjs prepare
   ```

   用户指定时使用，例如：

   ```bash
   node .agents/skills/eda-all-items-audit/scripts/run.mjs prepare --area '2S'
   node .agents/skills/eda-all-items-audit/scripts/run.mjs prepare --area 'S*min(3,max(2,1+S/400))'
   ```

   S 是正式 Host 准备完辅助设施后的设备总占地。公式支持 S、数字、括号、`+ - * / % **`、比较、三元条件，以及 `min/max/ceil/floor/round/abs/sqrt/pow/log/exp`（可写 `Math.` 前缀）。结果须为有限正数，向上取整并封顶 4900；70×70 边长约束继续由 Host 执行。公式用现有 TypeScript parser 解析为数学 AST，不执行传入的任意 JavaScript。

   【用户明确要求，2026-10-30】用 `prepare --search-mode 1|2|3|4` 选择本轮搜索模式，省略时默认 **2**，可与 `--area`、`--items` 等准备参数组合：

   | 模式 | 计算策略 |
   | --- | --- |
   | 1 | 完整结算累计 50M，已有次解也继续计算。 |
   | 2（默认） | 累计最多 50M，任何阶段找到正式验收的严格缩面积次解即停止当前物品。 |
   | 3 | 找到次解即停止；累计 50M 后每次追加 50M，依次达到 100M、150M……，直到次解出现。 |
   | 4 | 至少完整结算累计 50M，50M 内已出现次解也继续跑满；50M 后仍无次解则每次追加 50M，直到次解出现。 |

   四种模式均在累计发放 20M 额度后记录首阶段，实际次数与保留尾额分别保存；模式 3、4 没有搜索次数或健康计算的总时长上限，仍保留进度停滞、取消结算和资源清理保护。模式 4 是“实际至少 50M + 必须出现次解”的组合条件，不能用保留尾额凑够 50M，也不能用模式 3 的提前停止替代；这不意味着数学上保证存在次解或保证有限时间内找到。模式固定进入原始输入、manifest、结果和历史 meta，`run`/`resume` 不覆盖它；变更模式须准备新轮次。维护脚本不会自动替换已有冻结执行包。

4. `prepare` 从当前 Registry 生成清单及原生请求，冻结源码、资源、执行器和构建；工作区在准备/构建期间变化会失败，此时修复准备问题后重做，不使用半成品。报告的物品数量以当前清单为准，不能写死 216 或依赖旧轮次文件。
5. 执行全量队列，保留同一个控制器执行会话：

   ```bash
   node .agents/skills/eda-all-items-audit/scripts/run.mjs run
   ```

6. 启动 `run` 或 `resume` 后，Agent 在终端执行 `sleep 600`，等待十分钟，再检查控制器进程、`status`、日志及回收进度，并向用户汇报。任务仍在执行时重复此循环；发生故障时先按下文处理，再开始下一轮等待。`sleep 600` 使用可续接的终端会话，分段等待同一进程，单次工具等待不超过 60 秒，以便接收用户输入。不得结束 Agent 回合后只留下后台脚本，也不以落盘记录代替回来检查和汇报。
7. 队列结束后执行 `audit`。只有原始全量清单每项已结算、已回收且资源清理通过，才报告“全量执行完成”；首解/次解全部通过是另一项结论。存在跳过项时，如实报告完成数量、跳过名单及覆盖缺口，不把审计进程退出码 0 当作全量完成。

【用户明确要求，2026-10-26】Windows 专项单独占用 `.temp/playwright-test/browser-windows.lock`，不占用本机 `browser.lock`；本机和远端各自串行，允许不同机器同时执行。Windows 的浏览器空闲、PID 与端口检查继续在远端执行。`setup`、`prepare`、`run`、`resume` 共用 Windows 专用锁。

用户要求失败占多数时提前停止，可执行 `run --stop-on-failure-dominance 10`。仅统计完整结算且清理通过的项目，两阶段均达标才算成功，其余计失败；失败数严格大于参数且严格大于成功数时，在回收确认前设置停止标记，保证下一项不会启动。门槛与停止原因写入本轮 manifest 和历史 meta，`resume` 沿用门槛。该停止不修改算法、种子或预算。

比较先按算法目录的 Git tree 去重。各组使用相同物品、根种子规则、产率和搜索模式；模式 1、2 使用 20M/50M 门槛，模式 3 使用 20M 首解门槛并持续等待次解。用户指定使用各版本原始默认面积，因此不传 `--area`，记录实际 S 和初始面积。这比较各版本默认配置的整体表现，不将面积差异归因于搜索逻辑。旧版通过原生冷草稿检查点写入根种子，再首次导入，不移植已消耗检查点。

指定物品属于用户授权的小样本对照，不代表全物品覆盖，也不增加历史排除。对照汇总可保留在 `.temp/eda/all-items/comparisons/`，仅保存版本身份、物品指标和运行状态，不额外保存历史任务、蓝图或日志。完全相同的已完成算法、输入和搜索模式可复用既有实测结果，并注明来源；模式 2、3 找到次解可提前结算，其余未完成预算的执行保留实际消耗，不能冒充预算失败。各独立组之间仍需完成 audit 和资源清理，再启动下一组。

## 固定语义

- 每项独立冷启动，固定根规则按物品 ID 派生种子，24 CPU 并发、硬件 WebGPU。普通异步 Host 保留生产调度语义，固定种子不保证每次时序与成绩完全一致。
- 模式 1 固定完整结算累计 50M；模式 2、3 任意阶段一旦检测到正式验收的严格缩面积次解，立即通过 Host 取消当前物品的剩余计算，等待在途工作完整结算，保存实际计数和检查点，完成清理及回收后继续下一物品；即使首解晚于 20M，也在找到次解时停止，但首解仍判失败。20M 前已找到次解时不再进入第二阶段。同面积改善不触发停止，不能将此正常提前结束标为用户取消或执行故障。
- 模式 4 在实际累计 50M 前禁止因次解而取消或结束。累计已达 50M 后才按次解条件停止；50M 额度阶段仍有尾额使实际次数不足 50M，或还没有次解时，每次追加 50M，持续使用同一内存任务、请求和根种子。次解晚于 50M 仍按真实发现次数判次解通过，首解仍使用 20M 门槛；健康计算没有总时长上限。
- 【2026-10-30，正式 Host 契约核实】完整搜索批次可能不能耗尽阶段额度，剩余值保存在原生 `checkpoint.unspentEvaluations`，下次 `continuePlanning` 会自动合并。累计发放门槛仍为 20M、50M，模式 3、4 此后每次追加 50M；未提前取消的阶段必须满足“实际累计次数 + 保留尾额 = 累计发放额度”。追加量是新门槛减实际次数再减已保留尾额，不能把尾额重复授予，不能计作已计算或丢弃。记录每阶段原生尾额，审计同时核对真实计数、额度守恒和原生任务中的本阶段预算。模式 1 仍要求实际精确 50M；模式 2 在 50M 发放额度内无法再派发完整批次时按真实实际次数和尾额结算。模式 4 必须真实至少 50M，即使 50M 额度阶段已有次解也须继续到满足实际次数。阶段切换不导入检查点、不改算法或缩小搜索批次。在途工作结算后的实际次数可能高于次解发现或最低停止门槛，必须分别保留，不能伪装为精确 50M。
- 首解次数是 `areaHistory` 第一份正式验收成果的原生发现计数，须 ≤20M。次解次数是首次面积严格小于最早首解的成果发现计数：模式 1、2 须 ≤50M，模式 3 不设次数门槛，晚于 50M 发现仍按实际次数记为次解通过。同面积提升不算次解，20M 前已经缩面积也有效。两次发现计数均从该次冷启动累计。
- 复用正式 Host 的几何、物料及产率验收，验证引擎固定 `dense-v2`，每仿真秒 2 个真实 tick。不得用未验产的候选或阶段最佳计数替代上述成绩。
- 产线目标按选定配方单机满速名义产率；默认来源、整台运行消耗、植物回用、直线存取线、仓库取货口、流体暗管出口、固体协议储存箱、流体暗管入口沿用正式功能。包含全部已声明活动内容。
- 六项历史排除及已确认的选方约束在 `policy.json` 中注明来源；不得擅自增加排除。需求生成失败、正式预检拒绝及完整预算内首解/次解不达标照常记录，不触发故障重试。执行故障按下文最多重试一次，仍失败则跳过；旧尝试和实际消耗必须保留，不能伪装成消耗 20M、50M 或成功。
- Windows 使用交互式计划任务在已登录桌面启动有界面 Edge；逐项独立浏览器、CLI 与静态服务。前三个实际浏览器项目依次覆盖 desktop 2552×1315@1、mobile 764×345@3.125、tablet 711×665@3.125，均启用触控；后续 desktop。需求生成失败不消耗一个 Screen Profile 名额。
- 每项在 `finally` 中关闭浏览器/CLI、停止专属服务，只处理带本轮 profile/session 归属的进程，核对创建时间、PID 和端口。清理未通过不得进入下一项。不占用 5173，不触碰用户浏览器或其他服务。

## 保留策略（用户明确要求，2026-10-26；2026-10-30 调整为逐物品替换）

固定使用已经被 `.gitignore` 忽略的 `.temp/eda/all-items/`：

```text
history/<run-id>.csv          仅物品 ID、中文名、首解累计次数、次解累计次数
history/<run-id>.meta.json    每轮一份公式、种子规则、源码指纹和汇总
results/<item-id>/current.json       该物品最新已结算结果的轮次指针
results/<item-id>/<run-id>/          该物品的任务、证据、manifest、原始输入和回收校验记录
latest/manifest.json         最新轮次身份和冻结配置
latest/runtime/              最新一轮输入、运行状态、未结算现场及故障归档
latest/rows.json              最新一轮详细状态，不进入历史
```

找不到的次数为空值，不能填 0；CSV 只包含已经回收的项目，完整性看同轮 meta 的 `complete` 和覆盖数量。meta 保存 `searchMode`；模式 3、4 的 `totalLimit` 为 `null`，表示没有累计次数上限。晚于本模式门槛才发现的解保留实际次数，仍判该阶段失败。重试前把故障现场归档到 `latest/runtime/recoveries/`，在 manifest 的 `authorizedRestarts` 中记录物品、尝试次数、原因及已知消耗；跳过项记入 `skippedItems`。最终审计后把重试和跳过的精简统计补入同轮历史 meta。历史不嵌入任务、蓝图、完整日志、trace 或仿真报告。

【用户明确要求，2026-10-30】每个物品独立保留最后一份已结算结果，直到该物品的新结果获取完成才删除旧结果；不在新一轮启动时整体删除上轮结果。具体如下：

- `prepare` 在新构建准备成功、确认远端空闲并取得 Windows 专用锁后轮换 `latest/`，不清空 `results/`。首次遇到旧布局时，先把 `latest/tasks/` 与 `latest/runtime/collected/` 中已结算且清理通过的结果迁入按物品保留目录；迁移或校验失败即停止轮换，避免丢失旧结果。旧任务通过硬链接迁移，不复制大型任务文件。
- 新结果压缩回传后先校验 SHA-256，在临时目录完整解包，核对摘要、轮次、物品、搜索模式、任务版本与种子；正常已结算结果必须携带原生任务。保存原始输入、轮次 manifest、摘要与任务哈希的回收记录后，才迁入 `results/<item-id>/<run-id>/`，核验旧结果归属，原子更新 `current.json` 并记录待删除轮次，最后删除旧结果、清空待删除记录。切换前中断时旧指针有效；切换后删除中断时新结果有效，依据指针中的待删除记录继续清理，即使旧校验文件已被部分删除也可恢复。可替换的新结果完成替换及本轮成绩落盘后才确认远端回收。
- 只替换完整结算且清理通过的项目。预算内未找到解、需求生成失败、正式预检拒绝属于已结算结果，可以替换旧结果；执行故障、用户取消、清理失败或跳过不替换，现场继续留在本轮 `latest/runtime/`。未运行、尚未回收、未选入本轮的物品继续保留旧结果。
- 旧结果携带自己的 run-id、manifest 和原始输入，不能算作当前轮次成绩；审计只读取与当前 run-id 匹配且校验记录有效的结果。正常情况下每物品只保留一份已结算结果；替换期间短暂共存两份，完成切换后清理旧份。历史 CSV/meta 继续保留，不嵌入任务或完整证据。
- 远端新 `run` 只轮换其专属 `latest/`，但仍有未确认回收的摘要或任务现场时拒绝清空。同一轮 `resume` 不轮换目录。每项任务仍只保留最近一个已结算检查点，每阶段覆盖前一阶段检查点；不额外复制蓝图。确认本地结果和成绩落盘后移除远端该项副本，防止两端长期重复。完整运行结束清理测试构建和传输包。

本专项按本条覆盖通用“成功规划永久保留”的旧约定，不写入 `.temp/eda/success/`。其他专项历史目录不属于清理范围。临时打包和解包文件在 `.temp/.trash/eda-all-items/` 下，使用后清理。已被新结果替换的历史任务无法逐项重验，只能比较精简成绩；尚未被替换的各物品最后一份结果仍可读取。

## 中断与恢复

【用户明确要求，2026-10-30】在暂停的全物品队列中插入指定物品测试时，先确认旧队列停止、所属资源清理且已完成项目全部回收，再将两端的整个 `latest/` 原子移至本专项 `paused/<run-id>/`，保留原冻结构建、传输包、请求、状态和 SHA-256，不使用 `prepare` 覆盖旧队列。记录暂停清单，指定物品单独准备新轮次。专项结束并审计、清理后恢复旧目录和远端配置；只更新获授权的控制器校验记录，不改旧算法、输入、种子或浏览器包。用户要求自己恢复时，保持旧队列停止，不自动 `resume`。用户明确要求导出时，可在 `deliveries/<run-id>/` 提供蓝图和下载包，不改变任务权威来源。

恢复时仅对 manifest 的 `reuseCandidates` 中用户指定物品尝试跨轮复用。`result-reuse.mjs` 同时核对算法版本、冻结生产源码/资源/依赖指纹（`executionIdentity`）、配方、产率、请求、面积公式、根种子、检查点与实际成绩门槛；版本字符串相同不够，算法或输入不同不跳过。模式 4 的新结果若证明次解发现次数不超过 50M，可作为旧模式 2 的已验证来源；即使来源实际结算超过 50M，也必须原样保留实际次数和来源模式，不能冒充一次未超 50M 的模式 2 冷启动。来源阶段按其原始模式审计，目标首解/次解按目标门槛审计；次解在 50M 后才发现时不能作为旧模式 2 的通过依据。

复用仍保留原 run-id、搜索模式、任务哈希和真实次数，通过 `reusedItems` / 行内 `reusedFrom` 显式引用，不能改写原生任务或源摘要、不能计为冷启动。先持久化本地引用和历史，再向远端同步完成记录；同步中断时重入补齐，不重复计算。远端保留原全量清单，通过已完成摘要跳过该项目，不新增历史排除、不将执行故障计为完成。审计核对原证据和目标阶段要求；轮换时保留其来源，不额外复制大型任务。未登记、证据缺失、版本/输入或预算不匹配的项目照常执行。

```bash
node .agents/skills/eda-all-items-audit/scripts/run.mjs status
node .agents/skills/eda-all-items-audit/scripts/run.mjs stop
node .agents/skills/eda-all-items-audit/scripts/run.mjs resume
```

`stop` 等当前物品完整结算、清理和回收后停止；`cancel` 才立即取消当前项。正常停止后 `resume` 跳过已结算项目，使用原冻结构建和种子继续剩余清单；不运行 `prepare`。用户主动取消或要求停止时不得自动重开。

模式 3 的当前物品可能长期等待次解，`stop` 仍等当前物品结束；需要立即中断时使用 `cancel`。模式 3 不能因累计达到 50M 或总墙钟超过两小时被取消；进度停滞十分钟或取消未结算仍视为执行故障，禁止借“无限等待”掩盖故障。

模式 4 同样允许长期等待次解，使用相同的停止、取消和故障保护；50M 是最低结算要求，不是搜索上限。

本地控制器断线不等于远端结束，远端每项清理后最多等待 15 分钟回收确认。恢复先查看 `status`：远端同轮仍运行时接管观察，不重复启动；已完成但未回收时先校验回收，不能重跑已完成项目。

【用户明确要求，2026-10-27】执行故障由 Agent 检查后处理，每个物品在同一轮累计最多重试一次，即最多两次冷启动；`resume` 不清零次数，此前已获授权的重跑也计入上限。沿用原冻结构建、请求、种子及搜索模式，新冷启动单独计数，不与旧尝试相加。

1. 先确认原任务已停止、所属资源清理通过，并核对 run-id、PID、锁和端口。清理失败须先修复；资源归属或清理状态无法确认时停止并报告，不能以跳过为由启动下一项。
2. 回收并校验故障证据，保留已结算次数；无法确认的消耗记为未知，不能填 0。首次执行故障时，归档旧现场及摘要，只恢复该物品为待执行状态，保留此前成绩，再调用 `resume` 重试。
3. 重试仍发生执行故障时，归档第二次现场，记录 `skippedItems`，跳过该物品并继续后续队列。保持本地原始 `runtime/cases.json`、manifest 全量清单及所有原请求不变；只从远端待执行清单移除已记录的跳过项，并保留调整前的执行状态。不得增加 `excludedItems`、把跳过写成成功或伪造完整预算。
4. 当前 CLI 没有独立的 retry/skip 命令。Agent 在确认回收和清理后，只调整该故障项的运行状态、摘要和回收确认，使现有 `resume` 能继续；不重新 `prepare`、不重建算法。存在跳过项时，现有覆盖断言或审计可能报告未完成，须保留该结果并汇报实际覆盖，不能为转绿改写完成状态。

Host 检查点未必持久化全部内存指导池，不能将导入旧检查点的重跑宣称为连续运行。

Windows 专用锁因控制器异常退出而遗留时，仅在确认原 PID 已退出、锁标签属于同一 run-id、远端轮次一致后，使用 `resume --recover-lock` 接管。本机浏览器不阻止远端接管。不得手动删除归属不明的锁。清理失败需要按日志核对归属后修复，再继续。

用户在运行中明确授权调整控制器时，先 `stop` 等当前项结算和清理，再切换控制器并 `resume`。不得为了更新控制器而中断或重开当前冷任务，不得重新构建浏览器算法。保留原源码指纹及浏览器测试包 SHA-256，单独记录获授权的控制器文件旧/新哈希和原因，再更新对应执行器校验项；算法、请求、种子及冻结测试包继续使用原值。执行故障按上述一次重试及跳过规则恢复。仅修改技能文档时记录文档旧/新哈希并更新对应校验项，不中断正在运行的任务。
