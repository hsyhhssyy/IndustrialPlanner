# 更新日志写作规范

## 适用场景

- 新增 `public/changelog/` 下的 `.md` 更新日志文件
- 修改已有更新日志
- 更新 `public/changelog/index.json`

## 条目类型前缀

- `feat:` — 新功能
- `fix:` — 修复已有 bug

`dev:` 类内部改动（构建脚本、配置、CI、提示词等）不面向最终用户，**不出现在 changelog 中**。

## 核心规则

### 1. 只记录用户可感知的变化

changelog 面向最终用户，只记录 `feat:` 和 `fix:`。内部重构、工具链调整、changelog 自身更新等一律不出现。

### 2. 涉及物品/设备时必须使用 i18n 正式名称

日志中涉及物品、设备、配方等概念时，必须到 `src/shared/i18n/zh-cn/registry.ts` 中查询其真正的中文名称，严禁自行翻译。

### 3. 修复 bug 时描述终端表现，而非根因

`fix:` 条目应直接描述用户看到的错误现象，而非内部技术原因。例如：
- ✅ `修复反应池无法选择输出端口物品的问题`
- ❌ `修复反应池端口过滤条件不符的问题`

### 4. 多条改动必须全部列出

如果一次提交包含多个独立改动，日志中应逐一列出所有条目，不可只选取主要条目省略其余。

### 5. 条目格式

每条以 `- ` 开头，简短描述改动内容。不写技术实现细节，只写用户可感知的变化。

### 6. 区分手动内容与自动生成内容

部分 changelog 由用户手动撰写，AI 只负责追加基于提交日志自动生成的条目。

- **用户手动撰写的部分**：只读，不修改。包括用户写的标题、引言、章节、条目等。
- **AI 自动生成的内容**：统一放在文章末尾的 `## 其他改动` 章节下，以列表形式逐条列出。`## 其他改动` 不是文章最后一个章节——用户可能在该章节之后写结语、未来展望等内容，插入时应识别并放在正确位置。
- **去重**：在写入 `## 其他改动` 前，必须先通读用户手动撰写的部分。如果某个功能或 bug 修复已经被用户手动提及，则在 `## 其他改动` 中不再重复列出。

## 整篇日志创作指南

### 功能优先级与结构

1. **重点功能**：用户给出的功能列表即为重点功能，按用户给出的顺序排列——最先提到的最重要。
2. **其他变更**：用户未提及但属于本版本变更的内容，统一放在日志末尾的 `## 其他改动` 章节下，尽量简洁概括，一两句话带过即可，不要展开详述。
3. **去重**：某个变更已作为重点功能在前文详述，或已被用户手动提及的，`## 其他改动` 中不再重复。

### 语气与风格

- 参考贴吧 / NGA 的社区分享帖语气，但不要提及任何具体平台名称或平台相关概念（日志会同步发布到 B站专栏、贴吧、NGA、森空岛、TapTap 等多个平台）。
- 语气可以轻松、有交流感，但**不要过于口语化**，整体保持正式但不死板。
- **严禁**出现：卖惨、自曝缺陷、自我贬低；与软件功能无关的个人情绪表达；对游戏官方（鹰角）的抱怨或负面评价；"我还没玩到这里所以图不好看"之类暴露作者个人状态的表述。
- 可以适当使用玩家社区常用表达（如"小伙伴们""各位玩家"），但不宜过度。

### 配图规则

**方式一：Playwright 自动截图**——功能适合截图展示时，用 Playwright 截图：

- 截图聚焦在需要介绍的功能上，而不是整个页面；
- 保留一部分周围 UI 环境，让读者知道这是在哪里；
- 每一幅截图下方必须配一行说明文字，格式为：

```
![图片描述](./img/xxx.png)
> 图：说明该截图展示了什么场景下的什么功能。
```

**方式二：占位图**——功能比较复杂、拿不准什么图能表达清楚但又确实需要配图时，插入占位文字：

```
[一张XXXXXX的图片]
```

描述清楚希望这张图片传达什么内容，后续由人工配图。

### 参考

可以阅读 `public/changelog/` 下的历史日志了解结构和格式，但**不要被旧日志的语气影响**——语气以本规范为准。
