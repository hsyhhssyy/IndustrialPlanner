# 更新日志写作规范

## 条目类型与范围

- `feat:`：新功能。
- `fix:`：修复已有 bug。
- `dev:`：构建脚本、配置、CI、提示词等内部改动，不面向最终用户，禁止写入 changelog。

更新日志只记录用户可感知的变化。内部重构、工具链调整、changelog 自身更新等一律不出现。

## 名称与描述

涉及物品、设备、配方等概念时，必须到 `src/shared/i18n/zh-cn/registry.ts` 查询正式中文名称，禁止自行翻译。

`fix:` 条目应描述用户看到的错误现象，不描述内部技术根因。

- 正确：`修复反应池无法选择输出端口物品的问题`
- 错误：`修复反应池端口过滤条件不符的问题`

一次变更包含多个独立改动时，必须逐一列出，不能只保留主要条目。每条以 `- ` 开头，简洁描述用户可感知的变化，不写技术实现细节。

## 手动内容与自动生成内容

- 用户手动撰写的标题、引言、章节和条目只读，不得修改。
- AI 自动生成的条目统一放在 `## 其他改动` 章节，以列表形式逐条列出。
- `## 其他改动` 不一定是文章最后一个章节；用户可能在其后保留结语或未来展望，插入时必须识别正确位置。
- 写入前必须通读用户手动内容。已被手动内容提及的功能或 bug 不得重复列出。

## 完整日志结构

1. 用户给出的功能列表是重点功能，按用户给出的顺序排列。
2. 用户未提及但属于本版本的其他用户可感知变化，统一放入 `## 其他改动`，用一两句话简洁概括。
3. 已作为重点功能详述或已由用户手动提及的内容，不得在 `## 其他改动` 重复。

## 语气与风格

- 使用社区分享帖式的轻松交流语气，但不要提及具体平台名称。
- 保持正式但不死板，避免过度口语化。
- 禁止卖惨、自曝缺陷、自我贬低、与功能无关的个人情绪、对游戏官方的抱怨或负面评价，以及暴露作者个人进度的表述。
- 可以适度使用“小伙伴们”“各位玩家”等社区表达，但不得滥用。

## 配图

功能适合截图展示时，可以使用 Playwright 自动截图：

- 聚焦需要介绍的功能，不要只截整个页面。
- 保留必要的周围 UI，帮助读者理解所在位置。
- 每张图下方必须包含说明：

```markdown
![图片描述](./img/xxx.png)
> 图：说明该截图展示了什么场景下的什么功能。
```

功能复杂、暂时无法确定合适画面但确实需要配图时，使用正式占位说明：

```text
[一张XXXXXX的图片]
```

占位说明必须明确图片需要传达的内容，供后续人工配图。

可以阅读 `public/changelog/` 中的历史日志了解结构和格式，但语气以本规范为准，不得被旧日志带偏。
